# 生产领料、委外与移动端任务对账契约（后端）

## 业务边界

- 生产领料从**已下达的工单物料需求**选择行和本次数量生成草稿。数量不得大于该需求行尚未领用量；创建草稿不扣库存、不增加已领量。
- 领料单编码由服务端产生，租户内唯一并有数据库唯一索引。App 后续扫码只传入编码，服务端按当前租户检索，不信任客户端提供的租户 ID。扫码载荷格式与码制待 App 联调；当前仅输出可编码的单号文本。
- 仓库/批次/库位可用量不足时，草稿保留并返回缺口，用户通过采购申请、仓库调拨或委外加工补齐；不能透支库存，也不能把预期供应当作已在库。
- 过账提交先在 MySQL 同一事务写任务及 Outbox，再由 durable Topic 队列异步消费。在消费者事务里过账、写库存流水、更新工单物料已领数量和任务状态；成功后才认为领料完成。幂等键重复请求必须返回原任务，不得重复出库。
- 委外订单至少区分原料发出数量、加工完毕收回数量及未返回数量。发出与收回由库存单据分别过账；同批次/库位追溯和供应商追溯需在单据中保留。委外收货不等于质检合格，质量放行另行实现。

## 后续 App 对账

- 报工：`GET /api/work-report/jobs/{jobId}`。
- 领料：`GET /api/material-issue/jobs/{jobId}`。
- 质检：`GET /api/quality-inspection/jobs/{jobId}`。
- `queued` / `processing`：本地继续保留；`completed`：确认服务器事务提交后才可删除本地 SQLite 任务；`failed` / `dead-lettered`：保留本地记录供人工处置/纠正，不要用同一个业务操作生成新随机幂等键反复过账。
- HTTP 提交请求使用稳定 `Idempotency-Key`（App 本地 UUID）并存储服务端返回 jobId。服务器最多尝试 3 次，失败任务进入独立死信队列，同时保留失败原因和原始业务任务供人工排障。领料死信仅管理员可调用 `POST /api/material-issue/jobs/{jobId}/replay`；客户端不能自动重放，管理员应先核查库存、单据和原消息，确认没有已过账的业务效果。

## 上线注意

本仓库当前启动使用 EF Core `EnsureCreated`，**不会升级已有数据库结构**。新增实体必须通过可审计的增量迁移应用到已有库；不能对旧正式卷执行删除/重建来“升级”。测试应使用独立 `_e2e` 数据库/Compose 项目，不接入正式业务数据。RabbitMQ publisher confirms + 手动 ack + Outbox/Inbox 用于处理网络中断、重投造成的重复，不意味着单节点部署具备零数据丢失或高可用；上线前还需备份、监控、权限细分与灾备验证。
